# Shadow Git Repository System - Implementation Summary

## What It Does

The scheduler automatically snapshots your workspace when you submit a job, ensuring the job runs with the exact files that existed at submission time, even if you continue modifying them while the job is pending.

## Key Features

### Per-Workspace Shadow Repositories
- Each workspace gets its own `.scheduler-git/` directory
- `.scheduler-git` **IS** the git directory (contains `branches/`, `objects/`, `refs/` directly - no nested `.git` folder)
- Files tracked in-place using `git --git-dir` and `--work-tree` - no copying or duplication
- Completely independent from user's git repository (if they have one)

### Smart File Filtering (All Configurable)
- **Default file size limit**: 1 MB
- **Folder file count limit**: Skip folders with >1000 files
- **Data type-specific limits** (override default):
  - `.npy`, `.npz`: 10 MB
  - `.pkl`: 5 MB
  - `.json`: 2 MB
  - `.csv`: 5 MB
- **Always include**: `.py`, `.sh`, `.yaml`, `.json`, `.txt`, `.md`, `.toml`, `.ini`, `.cfg`, `.conf`, `.env`
- **Always exclude**: `__pycache__`, `.git`, `.scheduler-git`, `*.pyc`, build artifacts, logs

### Configuration

All settings can be overridden via Config object or config file:

```python
# In code
config.snapshot_max_file_size = 2 * 1024 * 1024
config.snapshot_max_files_per_folder = 500
config.snapshot_data_type_limits = {'.npy': 20 * 1024 * 1024}
config.snapshot_always_include_extensions = {'.py', '.yaml'}
config.snapshot_exclude_patterns = {'__pycache__', '*.pyc'}
```

```yaml
# In ~/.scheduler/config.yaml
snapshot_max_file_size: 2097152
snapshot_max_files_per_folder: 500
snapshot_data_type_limits:
  .npy: 20971520
snapshot_always_include_extensions: ['.py', '.yaml']
snapshot_exclude_patterns: ['__pycache__', '*.pyc']
```

## How It Works

### 1. Job Submission

When you submit a job from `/your/workspace`:

1. System checks if `.scheduler-git/` exists in workspace
   - If not found and no existing git repo: Prompts user to confirm workspace directory
   - Creates `.scheduler-git/` as a bare git repository (then sets `core.bare=false`)
2. Filters files based on size limits and patterns
3. Uses `git --git-dir=/your/workspace/.scheduler-git --work-tree=/your/workspace` to commit files
4. Creates branch `job-{job_id}` with the snapshot
5. Stores commit SHA as `job.snapshot_ref`

**Important**: Files stay in your workspace; only git metadata goes into `.scheduler-git/`

### 2. Job Execution

When the job runs:

1. Creates git worktree at `~/.scheduler/work/job-{job_id}/snapshot/`
   - **Worktrees** are isolated working directories from the same git repository
   - Each job gets its own worktree with files from its snapshot
   - Changes in one worktree don't affect others or the main workspace
2. Job executes in the worktree with only snapshotted files
3. After completion, creates another commit to capture changes
   - Small files produced are committed (if under size limits)
   - Large files are documented but content not preserved
4. Cleans up the worktree

**Why worktrees?** They provide complete isolation - multiple jobs can run simultaneously with different file versions without conflicts.

**Why `--work-tree`?** This flag tells git where the actual files are (user's workspace) while keeping git metadata separate (in `.scheduler-git`). It enables tracking files without copying them.

## Workspace Directory Selection

The system determines the workspace as follows:

1. **If user already has `.git`**: Use that directory as workspace
2. **If no `.git` found**: On first job submission, prompt user to confirm/select the workspace directory
3. Creates `.scheduler-git/` in the confirmed workspace

This ensures snapshots are scoped to the correct project boundary.

## Directory Structure

After job submission:

```
/your/workspace/
├── .scheduler-git/           # Shadow git repository
│   ├── branches/             # Git branches
│   ├── objects/              # Git objects  
│   ├── refs/                 # Git refs
│   │   └── heads/
│   │       ├── job-123       # Job snapshot branch
│   │       └── job-456       # Another job's branch
│   ├── config                # Git config
│   └── HEAD                  # Git HEAD
├── your_code.py              # Your files (untouched)
├── config.yaml               # Your files (untouched)
└── data.csv                  # Your files (untouched)
```

During job execution:

```
~/.scheduler/
├── work/
│   └── job-123/
│       └── snapshot/         # Git worktree for job-123
│           ├── your_code.py  # Files from snapshot
│           ├── config.yaml   # Files from snapshot
│           └── output.txt    # Generated by job
└── data/                     # Other scheduler data
```

Note: We use `~/.scheduler/work/` (not `/tmp/`) for worktrees to ensure they persist for job inspection and cleanup.

## Snapshot Lifecycle

### Submission Snapshot
- Created when job is submitted
- Contains filtered files from workspace
- Immutable - represents "what was intended to run"
- Stored in branch `job-{job_id}`

### Completion Snapshot (Future Enhancement)
- Created after job finishes
- Adds output files to submission snapshot
- Shows "what actually happened"
- Documents large files even if not preserved

## Limitations

### What's NOT Snapshotted
- Files over size limit (unless explicitly configured)
- Large datasets and models (users should use absolute paths to shared storage)
- Build artifacts and caches
- Folders with excessive files (>1000 by default)

### What's NOT Guaranteed
- System dependencies and packages
- Environment variables (unless explicitly saved in config files)
- State from other processes or services

Users requiring full environment reproducibility should combine snapshots with containers or virtual environments.

## Benefits

✅ **Zero User Impact** - Your files and git state never modified
✅ **No File Duplication** - In-place tracking saves disk space
✅ **Complete Isolation** - Each job runs independently via worktrees
✅ **Disk Efficient** - Smart filtering + git delta compression
✅ **Fully Configurable** - Adjust all limits and patterns
✅ **Works Anywhere** - Not limited to git repositories
✅ **Easy Inspection** - Jobs are git branches, use standard git tools

## Example Workflow

```bash
# User working in /project
cd /project

# Submit job (creates .scheduler-git/ if needed)
scheduler submit --req 2 train.py

# User can immediately continue working
vim train.py  # Modifications won't affect queued job
git commit -am "New approach"  # Your git is independent

# Later, job runs with files from submission time
# Job executes in ~/.scheduler/work/job-abc123/snapshot/

# User can inspect what actually ran
cd /project
git --git-dir=.scheduler-git log job-abc123
git --git-dir=.scheduler-git show job-abc123:train.py
```

## Security & Disk Management

### Security
- Shadow repos respect file permissions
- Sensitive files should be in exclusion patterns (`.env`, `credentials.*`)
- Shadow repos are user-owned and isolated

### Disk Management  
- Monitor `.scheduler-git/` size in each workspace
- Clean up old job branches: `git --git-dir=.scheduler-git branch -D job-old-id`
- Git's delta compression keeps similar snapshots efficient
- Consider periodic `git gc` in shadow repos
